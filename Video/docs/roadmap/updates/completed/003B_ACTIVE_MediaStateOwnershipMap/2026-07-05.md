## MediaState — single owner

`MediaState` is constructed once per `MediaSession` (`MediaSession.cs:14`) and
the same instance is shared by reference into `AudioPipeline`, `CdgPipeline`,
and `VideoPipeline` via their constructors. `PlaybackCoordinator` exposes it
through `State` (`PlaybackCoordinator.cs:31`); `PipelineMediaEngine` reads it
for `Content` / `State` / `IsOpen` (`PipelineMediaEngine.cs:49-51`). There is
no second `MediaState` instance for the active session — all writers operate
on the shared object.

## State ownership conflicts / ambiguity

1. **`PlaybackState` has multiple writers per pipeline.** For audio, both the
   caller-thread transport methods (`Play/Pause/Stop`, rows 7-9) and the BASS
   sync event handler `OnAudioStateChanged` (row 12) / `OnAudioPlaybackEnded`
   (row 16) write `PlaybackState`. For video, both the transport methods
   (rows 27, 29, 30) and the presentation-loop `CompletePlaybackAtEnd`
   (row 32) write it. The transport methods and the engine-event callbacks
   are **not serialized against each other** — `MediaState.SetPlaybackState`
   only does an equality short-circuit, no lock. This is the primary
   ownership ambiguity: final playback state is owned by *whichever writer
   ran last*, and the transport path and the end-of-media path can race.

2. **`PositionSeconds` is written from at least three threads for video.**
   Transport `Stop` (row 30, caller thread), `TryRestartLoopPlayback`
   (row 28, caller or presentation thread), `SeekCore` (row 31, seek worker),
   and `CompletePlaybackAtEnd` (row 32, presentation thread) all write
   position. `MediaState.SetPosition` has no lock; it relies on the
   `0.001s` equality guard. Concurrent writes from the seek worker and the
   presentation loop are possible during scrubbing.

3. **`SetOpened` is called twice for the same open in some paths.**
   `PlaybackCoordinator.OpenAudioCdg` (rows 33-34) calls `State.SetOpened`
   directly *after* `AudioPipeline.Open` already called `SetOpened` (row 4/6)
   on success. The second call overwrites `Content` with `Audio|Cdg` (or
   `Audio|Cdg|Archive`). For pure-audio opens, only the `AudioPipeline`
   call runs. This is intentional but means `Content` ownership is split
   between `AudioPipeline` (audio-only) and `PlaybackCoordinator`
   (audio+cdg pairing). `CdgPipeline.OpenPaired` (rows 17-18) does **not**
   call `SetOpened` — it only adjusts duration/position — so the CDG
   pipeline never owns the `Content` flags for a paired open.

4. **Image opens bypass the pipelines entirely.** `PipelineMediaEngine`
   (rows 35-36) writes `MediaState` directly via `_coordinator.State.SetOpened`
   after calling `_coordinator.Close()`. No pipeline is attached for images,
   so `MediaState` is owned solely by `PipelineMediaEngine` for image content.
   This is the one place a writer outside the three pipelines mutates state.

5. **`MediaSession.Clear` resets state after pipelines close.** Row 1 runs
   `State.Reset()` *after* `Audio?.Close()` (which already calls `State.Reset()`
   via row 11/14). Double-reset is harmless but means the reset is owned by
   both `MediaSession` and `AudioPipeline` for audio content.

6. **`MediaControls.MediaStopped` vs `MediaEnded` semantics.** `MediaStopped`
   fires only on user-initiated `Stop()` (`MediaControls.cs:112`).
   End-of-media fires `MediaEnded` (and `MediaStarted` again if looping).
   `MediaState.PlaybackState` is set to `Stopped` by **both** paths
   (rows 9/16 for audio, 30/32 for video), so the public `State` property
   cannot distinguish "stopped because user pressed stop" from "stopped
   because media ended." Hosts that need that distinction must rely on the
   events, not on `State`.

7. **`MediaControlPlayer.MediaEnded` is marshaled through the operation
   queue; `MediaStarted` and `MediaStopped` are not.** This means a host
   could see `MediaStarted` (synchronous, caller thread) before the
   queued `MediaEnded` from the previous item finishes dispatching. The
   event ordering is not guaranteed to match the underlying state
   transitions when the operation queue is busy.

## Recommendation for next implementation stage

The mapping exposes two concrete, separable problems that should be the next
stages. They are independent and should be staged separately:

**Stage 003C — `MediaState` thread-safe accessors.** Add a `Lock` to
`MediaState` (the codebase already uses `System.Threading.Lock` everywhere
else) and guard `SetPlaybackState`, `SetPosition`, `SetDuration`, `SetOpened`,
`Reset`, and the property getters. This is the smallest safe change that
removes the row 12/16, row 31/32, and row 28/32 races without altering event
threading or public API. No behavior change, only synchronization. Low risk,
build-verifiable, no manual smoke test required beyond confirming playback
still works.

**Stage 003D — Consolidate `SetOpened` ownership.** Pick a single owner for
`Content` per open path: either the pipeline that first opens
(`AudioPipeline`/`CdgPipeline`/`VideoPipeline`) or the `PlaybackCoordinator`
for paired/compound content. Today the audio+cdg pairing path writes
`SetOpened` from both `AudioPipeline` (audio-only flags) and
`PlaybackCoordinator` (audio+cdg flags), and the CDG pipeline never writes
`Content` for paired opens. This is a behavior-affecting refactor and should
be staged after 003C, with a manual smoke test for audio, audio+cdg,
standalone cdg, video, and image opens.

A separate, lower-priority stage (003E) could unify the `MediaEnded` /
`MediaStopped` / `MediaStarted` marshaling so all three go through the
operation queue (or all three stay synchronous), to fix the ordering issue
in note 7. This touches public event threading and should not be combined
with 003C/003D.

## Notes

- `MediaState` is `internal sealed` and lives in `FatzBombMedia.MediaControl.Pipeline`. All writers are inside the same assembly, so adding a `Lock` is non-breaking.
- The `System.Threading.Lock` pattern (already used in `CdgPipeline` and `VideoPipeline`) is the established synchronization primitive in this repo; `MediaState` is the only shared mutable pipeline state object that does not use it.
- Graphify (`graphify-out/graph.json`) was queried for `MediaState` writers but the traversal only surfaced the type node and did not resolve per-method callers; the writer table above was built from direct grep + file reads, which is authoritative for this mapping.
