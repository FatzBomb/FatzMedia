# Stage Update

Stage: 005C — Decoder Device-Lost Recovery
Date: 2026-07-06

## Review conclusion

Stage detects and recovers loss of the FFmpeg-owned hardware-decode D3D11
device, separately from the Stage 005B presentation-device recovery. Rather
than rebuilding the FFmpeg device in place (FFmpeg owns it; Core cannot
recreate it safely), the decided approach is a runtime software-decode
fallback: the live decoder is swapped for a software one at the current
transport position, audio and CDG keep running uninterrupted, and a slow
background re-probe swaps back to hardware when the GPU returns. Detection
requires both repeated hardware-path decode failures AND a confirming
device-removed reason, so a bad stream never triggers fallback. The fallback
also breaks the 005B feedback loop by stopping the flow of lost-device
hardware frames to the presentation side.

## Changed

- `D3D11DeviceLostClassifier` — new `IsDeviceLost(IntPtr)` overload for the
  raw FFmpeg-owned native device pointer (never false-positives on null or
  unwrappable pointers).
- `VideoDecoder` — consecutive hardware-decode-failure counter with
  `IsHardwareDecodeRepeatedlyFailing` (threshold 3), reset on success/Close.
- `VideoPipeline` — dedicated recovery scheduler, debounced detection in the
  decode loop, software-decode fallback via `SwapVideoDecoder` (reuses the
  seek stop-reposition-restart path under `_transportGate`), 5s hardware
  re-probe/restore, bounded retry (3 attempts, 500/1000/2000ms), deterministic
  scheduler teardown in `Close()`/`Dispose()`.
- `VideoEngineState.Error` — new additive enum value, raised only when
  recovery is exhausted.
- Diagnostics: `"Decoder.DeviceLost"` (Error/Info) and terminal
  `"Decoder.DeviceLost.RecoveryFailed"`.
- 1 new classifier test (`IntPtr.Zero` path); removed the 005C line from
  `docs/roadmap/STAGE_MANIFEST.md`.

Full details in `docs/roadmap/completed/005C_BACKLOG_DecoderDeviceLostRecovery.completed.md`.

## Still open

- Manual smoke test of a simulated device-lost condition (GPU adapter
  disable/re-enable or driver TDR) during hardware-decoded video — the shared
  outstanding validation gap for Stages 005A/005B/005C. Requires real
  hardware; cannot be automated. See `docs/VALIDATION.md` section 7, item 12.
- Device-lost surfacing only via `avcodec_send_packet` is not counted toward
  the failure threshold (pre-existing observation gap; extend if seen).
- `HardwareDecodeReprobeInterval` (5s) is a hard-coded constant; move to
  configuration only if a host needs a different cadence.

## Notes

- Audio is deliberately left running during the decoder swap so a venue show
  is never interrupted; CDG overlays are rendered by Core's CDG pipeline, not
  the FFmpeg decoder, so they also keep running.
- Loading a new file restores hardware decode automatically through the
  normal `Open()` → `FromConfiguration` (`Auto`) path; the software fallback
  is scoped to the current decoder instance only.
