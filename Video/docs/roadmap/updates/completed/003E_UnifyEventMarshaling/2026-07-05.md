# Stage Update — 003E Unify Event Marshaling

Stage: 003E — Unify Event Marshaling
Date: 2026-07-05

## Changed

- `FatzBombMedia.MediaControl/Api/MediaControlPlayer.cs` — `OnControlsMediaStarted` and `OnControlsMediaStopped` now route through `_controlOperations.Enqueue`, matching the existing pattern in `OnControlsMediaEnded`. All three public events (`MediaEnded`, `MediaStarted`, `MediaStopped`) now fire on the `MediaControlOperationQueue` worker thread, serialized in the order they were raised.

Previously, `MediaStarted` and `MediaStopped` were raised synchronously on the caller thread (UI thread for user-initiated Play/Stop, or render thread for loop-restart `MediaStarted`), while `MediaEnded` was already queued. This created an ordering hazard: a host could see `MediaStarted` for the next item before the queued `MediaEnded` from the previous item finished dispatching.

No public API changed. Event signatures, event names, and `IMediaControlSession` are unchanged.

## Rationale

The 003B mapping (finding 7) identified that `MediaControlPlayer.MediaEnded` was marshaled through the operation queue but `MediaStarted` and `MediaStopped` were raised synchronously. This meant event ordering was not guaranteed: during loop restart, `HandleMediaEnded` fires `MediaEnded` (queued) and then `MediaStarted` (synchronous), so `MediaStarted` could reach the host before `MediaEnded`.

Routing all three through the same queue ensures:
1. Events fire on a single thread (operation queue worker), not mixed caller/render/background threads.
2. Events are serialized in raise-order.
3. Hosts only need to marshal from one thread context (operation queue) instead of multiple.

The WPF adapter (`MediaSurface`) already marshals all three events via `Dispatcher.BeginInvoke` (`MediaSurface.cs:299-318`), so it does not assume a specific thread for any of them. The Player host does not subscribe to these events directly. No existing handler depends on synchronous delivery.

## Notes

- `PresentationFramePresented` is intentionally NOT routed through the operation queue. It fires on the render thread at frame-presentation cadence (potentially 60+ Hz) and marshaling it through the operation queue would add latency and backpressure to the presentation path. `MediaSurface.OnSessionPresentationFramePresented` already marshals to the UI thread via `Dispatcher.BeginInvoke`.
- The `null-handler` early return in `OnControlsMediaStarted`/`OnControlsMediaStopped` avoids enqueueing a no-op when no subscriber is attached, matching the existing `OnControlsMediaEnded` pattern.
- `MediaControlOperationQueue` is a dedicated worker thread; events are delivered sequentially, not concurrently.
